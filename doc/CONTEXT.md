## Цель и ограничения курса

Учебная поисковая система по курсу «Информационный поиск» МАИ.
Корпус — русскоязычные и англоязычные публикации о видеоиграх: новости,
статьи, обзоры, блоги. Старый корпус текстов песен больше не используется.
Цель — собрать более миллиона документов и обрабатывать корпус потоково.

- Общие требования: `doc/course_info.md`; задания: `doc/homework_*.md`.
- Основные компоненты поиска — C/C++ без STL; для токенизации STL разрешена.
  Структуры индекса и поиска реализуем самостоятельно.
- Python используется для робота, HTML-парсеров, подготовки данных и обвязки.
- Ввод и вывод — UTF-8. Основные тесты C++-компонентов — GoogleTest на C++.
- Требование курса о длине статей нужно учитывать отдельно: в нашем корпусе
  много коротких новостей; число документов само по себе не доказывает
  соответствие всем требованиям.

## Главное, что сделано в предыдущих лабораторных

- **ЛР1–ЛР2 — сбор корпуса.** Определены восемь игровых источников; написаны
  HTML-парсеры и робот. Sitemap, очередь `frontier`, повторные попытки,
  повторный обход и раздельная загрузка/обработка HTML переживают перезапуск.
  Оригинальный HTML архивируется отдельно, готовые тексты хранятся в MongoDB.
  Для лабораторных по поиску используется завершённый локальный снимок, поэтому
  работа робота, MongoDB и диск E для повторения поиска не требуются.
- **ЛР3 — токенизация.** C++ `gaming-v3` обрабатывает русский и английский UTF-8,
  возвращает нормализованный токен, номер позиции и байтовые границы исходного
  текста. Это основа всех дальнейших индексов. Правила для игровых названий,
  версий, C++/C# и `S.T.A.L.K.E.R.` проверены GoogleTest; есть CLI-демо.
- **ЛР4 — лемматизация.** Свой C++-анализатор использует подготовленные
  OpenCorpora/WordNet данные, сохраняет все различные разборы и исходную форму.
  На диагностическом снимке словарное покрытие 81,29% токенов; это **не**
  точность поиска. Есть показ «токен → лемма/леммы», C++ GoogleTest и отдельная
  оценка на размеченных заголовках. `Джозеф → Джо` — синонимия, а не
  лемматизация. Пример на большом индексе: `Mimir AND has AND returned` даёт
  0 документов по словоформам и 7 по леммам; разметки релевантности для этих
  семи нет. Отчёт ЛР4 дополнен в коммите ЛР8; см. `doc/report_lab4.tex/.pdf`.
- **ЛР5 — закон Ципфа.** На фиксированном снимке из 478 833 документов C++
  посчитал 158 544 765 токенов, 1 451 704 словоформы и 715 896 hapax.
  Показаны наблюдаемые частоты, теоретическая модель $C/r$ и отдельная
  МНК-аппроксимация $C/r^\alpha$ в логарифмах на рангах 10–10000; это
  регрессия частоты по рангу, а не ранга по частоте. В итоговом отчёте оставлены
  словоформы, весь корпус, сайты и языки. Эксперименты с леммами и типами
  публикаций сохранены отдельно, но не включены в итоговый отчёт.
- **ЛР7–ЛР8 — индекс и булев поиск.** Один физический индекс содержит два
  пространства терминов — `surface` и `lemma`, собственные списки ID для
  каждого термина и общую таблицу документов. Словарь ищется на диске;
  операции AND/OR/NOT выполняются потоково. В обоих пространствах используются
  тот же разбор запроса и те же булевы операции; меняются нормализация термина
  и выбранные списки. CLI читает UTF-8 строки из stdin и пишет JSONL, а
  `serve_search.py` даёт HTML-форму поверх C++-движка. Булева выдача
  отсортирована по ID; отдельный режим TF-IDF добавлен в ЛР13.
  Разница числа совпадений не доказывает рост релевантности. Самостоятельный
  `NOT` требует обхода универсума; `A AND NOT B` ускорен в ЛР12.
- **ЛР10 — цитатный поиск.** Добавлены 335 548 564 координаты и фразы в
  кавычках как операнды булевых выражений. Слова фразы должны идти подряд и
  в заданном порядке внутри одного поля (`title` или `body`); совпадение
  нормализованных токенов не означает побайтовую цитату. Лемматизация меняет
  допустимые формы слов, но сохраняет порядок и соседство. Например,
  `"god of war"` и `"war of god"` дают разные результаты.
- **ЛР11 — сжатие.** Измерения и реализация описаны в разделе ниже.
  Ключевое различие: список **ID документов** термина — часть индекса;
  коллекция MongoDB `documents` и корпус текстов им не являются.
- **ЛР12 — ускорение.** Указатели позволяют пропускать части длинных списков;
  для `A AND NOT B` используется разность списков без обхода универсума.
- **ЛР13 — ранжирование.** Схема `lnc.ltc`: логарифмический TF,
  IDF запроса, полная косинусная нормировка документов и top-k.
  Булев AND и TF-IDF имеют разные правила включения документов; OR
  использовался только как база сравнения времени на одинаковых кандидатах.

ЛР8 `4f1ad7e`, ЛР10 `d4c158f`, ЛР11 `f9504ce`, ЛР12 `c89b4e4`,

## Источники и устройство робота

Источники: `stopgame`, `playground`, `ixbt_games`, `igromania`, `pcgamer`,
`eurogamer`, `gamemag`, `gamingonlinux`.

- Входная команда — `crawler.py`, логика — `src/crawler.py` и
  `src/crawl_scheduler.py`; HTML-парсеры — `src/parsers/`.
- `src/discovery.py` скачивает и разбирает XML-карты. Робот сам обновляет
  sitemap по сроку каждого сайта; расписание хранится в MongoDB и переживает
  перезапуски. Интервал сейчас 24 часа, а не полный обход при каждом запуске.
- Локальный инвентарь: `data/discovery/inventory_all/url_inventory.tsv`.
  Это список найденных URL; рабочая очередь находится в БД, в `frontier`.
- Состояния очереди: `pending`, `in_progress`, `done`, `retry`, `gone`,
  `blocked`, `excluded`. Ошибки скачивания и ошибки разбора — разные состояния.
- В `crawler.large.yaml`: 4 потока скачивания, максимум один запрос к одному
  сайту одновременно; глобальная задержка 0,5 с, локальная 3 с, StopGame 5 с.
  Учитывается Crawl-delay из robots.txt; отдельной задержки «после robots» нет.
- `parse_mode: deferred`: робот сохраняет HTML, отдельный `parse_worker.py`
  выделяет текст и метаданные. Оба процесса можно запускать одновременно.
- Повторный обход по сроку — `revisit.py`: используются HTTP-валидаторы и хеш
  содержимого, изменённая версия отправляется на повторный разбор.

## Хранение и место на дисках

MongoDB 8 работает через `compose.yaml`: `mongodb://127.0.0.1:27017`, БД `mai_ir`,
именованный том `mai-ir-mongo`.

- `documents` — обработанный документ: `parsed.title`, `parsed.text`, теги,
  даты, URL и служебные поля. `indexable: false` отмечает непригодные записи.
- `raw_pages` — HTML и метаданные загрузки либо ссылка на внешний архив.
  Версии raw и parsed связаны через ID, хеш, `raw_generation`, `fetched_at`.
- `frontier` — очередь; `crawler_meta` — расписания и служебное состояние;
  `raw_archives` — каталог архивных пачек.
- Диск Docker: `D:\Kirbass\AppData\DockerDesktopWSL\disk\docker_data.vhdx`.
  Внешний отключаемый диск E: содержит `E:\Kirbass\MAI-IR\raw_archives`.
- Перенос raw: экспорт BSON → полная проверка архива и восстановления образцов
  → замена HTML ссылками. Готовые тексты и очередь остаются в MongoDB.
  Для повторного разбора архивных страниц E: должен быть подключён.
- Резерв робота и парсера в большом конфиге — **4,5 ГиБ** на контролируемых
  дисках. Порог не снижать автоматически. Для переноса можно явно задать
  отдельный резерв обслуживания; это не изменение YAML.
- Архивирование освобождает место внутри WiredTiger. Свободное место Windows
  может не увеличиться: сжатие Docker VHDX — отдельное обслуживание с остановкой
  MongoDB/Docker, fstrim и правами администратора. Оно не удаляет документы.
- `data/`, `.venv/`, `build/` исключены из Git. Большие данные не коммитить.

## Основные команды

Из корня проекта, с активированной `.venv`; Docker Desktop должен работать:

```bash
docker compose up -d mongo
python crawler.py crawler.large.yaml
python parse_worker.py crawler.large.yaml --follow
python crawler_status.py crawler.large.yaml
```

Робот и парсер запускаются в разных терминалах. Сейчас `max_documents: 60000`,
`run_forever: false`: это ограничение одного запуска, а не всей очереди.

После остановки робота и парсера, с подключённым E: и работающей MongoDB:

```bash
python archive_raw.py crawler.large.yaml --auto --maintenance-reserve-gib 4
```

Команда выбирает новую пачку или продолжает готовую после прерывания.
Один запуск обрабатывает одну пачку. Подробности — `doc/raw_archives.md`.

```bash
python -m pip install -r requirements-dev.txt
python run_tests.py --lab all
python run_tests.py --lab 11 --cpp-only
docker compose run --rm --no-deps tokenizer-tests compression_tests --gtest_color=yes
```

Последняя команда запускает уже собранные GoogleTest. Имена исполняемых файлов
без `/build/` удобны в Git Bash: он иначе преобразует Linux-пути в Windows-пути.
Для установки пакетов использовать `python -m pip`: старый `pip.exe` однажды
сломался после перемещения виртуального окружения.
