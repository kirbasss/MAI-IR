# ЛР3: токенизация

Основной алгоритм написан самостоятельно на C++17. STL используется только
в модуле токенизации, что разрешено требованиями курса. Python экспортирует
корпус из MongoDB, запускает CLI-тесты и эксперименты; matplotlib строит график.
Лемматизация/стемминг и закон Ципфа остаются для следующих работ.

## Подготовка и полный запуск

Нужны Python с зависимостями и `g++` либо `clang++` в `PATH`.
При необходимости путь к компилятору задаётся переменной `CXX`.

```powershell
python -m pip install -r requirements-lab3.txt
docker compose up -d
python run_lab3.py --config crawler.large.yaml --output data/tokenization/run_001 --report-dir doc/lab3
```

Команда собирает программу с `-std=c++17 -O3 -DNDEBUG`, запускает автотесты,
экспортирует пригодные документы, сохраняет токены, статистику, сырые замеры
и график. Каталог `--output` должен быть новым: прошлые результаты не
перезаписываются. Опция `--report-dir` явно обновляет небольшие файлы для
отчёта; тексты, URL и токены туда не копируются.

Существующий снимок можно использовать повторно:

```powershell
python run_lab3.py --snapshot data/tokenization/mongodb_2026-10-21 --output data/tokenization/run_002 --report-dir doc/lab3
```

Для автономного запуска без MongoDB есть `--parsed-dir data/parsed`.
Это другой входной корпус: его размеры и результаты будут отличаться.
Экспорт не изменяет коллекции MongoDB. Он читает только пригодные документы
без ошибки парсера и только поля заголовка, текста и небольшие метаданные.
Документы без текста, но с заголовком сохраняются. Пустые записи пропускаются.
Для согласованного снимка лучше экспортировать при остановленном краулере:
обычное чтение MongoDB не является транзакционным снимком всей коллекции.
В manifest сохраняются начало и конец экспорта. Даже если обкачка продолжается,
последующие измерения и демонстрация используют один завершённый локальный файл.

## Демонстрация на защите

```powershell
python demo_lab3.py
```

Команда сама выбирает самый новый завершённый снимок из `data/tokenization`.
MongoDB и сеть для демонстрации не нужны. Исполняемый файл C++ автоматически
пересобирается, если изменились исходники или хеш бинарного файла.
Python только выбирает статьи и оформляет вывод; токены выдаёт тот же
C++-модуль, что используется при обработке всего корпуса.

Показываются три реальных примера: версия, обозначения C++/C# и нормализация
S.T.A.L.K.E.R. в `stalker` (либо Half-Life, если названия с точками не найдены).
Заголовки и URL берутся из снимка; фрагменты не переписываются вручную.
В таблице `original` — исходная подстрока, `normalized` — терм после обработки.
Позиции начинаются с нуля внутри **целого поля статьи**, а байтовые
полуинтервалы `[начало,конец)` относятся к его исходному UTF-8 представлению.
Например, русская буква обычно занимает два байта. Над фрагментом указаны
его границы в том же поле.

Можно выбрать свой пример и сохранить журнал:

```powershell
python demo_lab3.py --find "3.0.1" --context 4
python demo_lab3.py --snapshot data/tokenization/mongodb_2026-10-21 --document-id 816 --find "3.0.1"
python demo_lab3.py --document-id 816 --field title
python demo_lab3.py --output data/tokenization/demo_001.txt
```

ID 816 относится к снимку от 21 октября; в другом снимке он может означать
другую статью. `--context` задаёт число соседних токенов с каждой стороны.
Файл `--output` должен быть новым и сохраняется в UTF-8. Если выражение
не встречается в корпусе, демонстрация не подставляет выдуманный пример.

## Отдельные команды

```powershell
python build_tokenizer.py
python -m unittest -v tests.test_corpus_export tests.test_tokenizer tests.test_lab3_demo
python export_corpus.py --config crawler.large.yaml --output data/tokenization/snapshot_001
build/tokenizer.exe corpus data/tokenization/snapshot_001/corpus.bin --output data/tokenization/tokens_001.tsv --stats data/tokenization/stats_001.json
python benchmark_tokenizer.py data/tokenization/snapshot_001 --output data/tokenization/benchmark_001 --runs 5
```

На Linux имя исполняемого файла — `build/tokenizer`. Для одного UTF-8 текста,
в том числе будущего поискового запроса, предусмотрен режим `text`:

```bash
printf 'GTA VI, Half-Life и ЁЖ\n' | build/tokenizer.exe text
```

В этом режиме TSV идёт в stdout, JSON со статистикой — в stderr.
Для проверки точных байтовых смещений в Windows предпочтительно передавать
UTF-8 файл через перенаправление Git Bash: старая PowerShell может
перекодировать текст в конвейере. В режиме `corpus` stdout содержит JSON,
а токены записываются только при `--output`. Есть `--limit N` для первых N
документов. Существующие файлы результатов программа не перезаписывает.
Обрезанный формат и повреждённый UTF-8 приводят к ненулевому коду возврата;
частичный файловый вывод не публикуется. В stdout до ошибки могли попасть
токены уже обработанного префикса — всегда проверяйте код возврата CLI.

## Запуск и устройство тестов

Тесты написаны на стандартном Python `unittest` в `tests/test_tokenizer.py`.
Они запускают настоящий C++-файл через `subprocess`: передают UTF-8 текст
в stdin, читают TSV из stdout и JSON со статистикой из stderr, после чего
сравнивают токены, позиции, границы и счётчики с заранее заданным результатом.
Подмены токенизатора Python-реализацией нет. При первом запуске или изменении
исходников C++ автоматически пересобирается; необходим компилятор в PATH.

Только тесты токенизатора:

```powershell
python -m unittest -v tests.test_tokenizer
```

Один конкретный тест нового правила:

```powershell
python -m unittest -v tests.test_tokenizer.TokenizerCliTests.test_dotted_acronyms_three_or_more_letters
```

Все проверки ЛР3 (экспорт, токенизация и демонстрация):

```powershell
python -m unittest -v tests.test_corpus_export tests.test_tokenizer tests.test_lab3_demo
```

Все тесты проекта: `python run_tests.py`. Для проверок ЛР3 MongoDB и сеть
не нужны: используются маленькие тестовые снимки и временные каталоги.
Реальные короткие фрагменты с ожидаемыми токенами сохранены в
`tests/fixtures/tokenizer_cases.json`. Повреждённый UTF-8 и формат проверяются
по ненулевому коду возврата, а ошибочный вывод не должен оставлять частичный файл.

## Правила gaming-v3

- Слово состоит из букв ASCII, русских букв `А–Я`, `а–я`, `Ёё`, латиницы
  Latin-1 и Extended-A, а также ASCII-цифр. Остальные письменности пока
  считаются разделителями. Расширение таблиц — отдельное изменение версии.
- ASCII, русский алфавит и поддержанные пары латиницы приводятся к нижнему
  регистру независимо от системной локали. `Ё` → `ё`, но `ё` не заменяется
  на `е`. Исключение `İ` сохраняется: полного Unicode case folding нет.
- Внутренние `'`, `’`, `ʼ` нормализуются к `'`. Внутренние `-`, `‐`, `‑`
  нормализуются к `-`. Соединитель сохраняется только между частями слова;
  последовательные соединители разделяют слова. Среднее и длинное тире
  являются разделителями.
- Отдельные `C++`, `C#` и варианты с ASCII-номером стандарта (`C++17`, `C#12`)
  сохраняются с символами `+`/`#`: `c++`, `c#`, `c++17`, `c#12`.
  Это узкое правило для `C`/`c`, а не сохранение произвольных плюсов:
  `a+b` разделяется на `a`, `b`; `abc++` даёт `abc`. `C+++`, `C##`
  и слитное `C++Builder` не распознаются как эти специальные токены.
- В числовой последовательности сохраняется точка, перед которой и после
  которой есть цифры. `3.0.1` — один токен; `V1.2.3` → `v1.2.3`.
  Начальная и конечная точки, повторные точки и точки между обычными словами
  остаются разделителями. Поддерживается существующее соединение с суффиксом
  через дефис: `3.0.1-rc1`. Это не семантический анализ версий: `1.5` и
  `127.0.0.1` также остаются целыми числовыми последовательностями.
- Цепочка из не менее трёх одиночных поддерживаемых букв через точки
  нормализуется удалением точек и приведением регистра: `S.T.A.L.K.E.R.` →
  `stalker`, `U.S.A` → `usa`, `А.Б.В.` → `абв`. Последняя точка необязательна.
  Пробелы внутри цепочки не допускаются. Две буквы (`A.B`) не склеиваются;
  многобуквенные сегменты (`ab.cd.ef`) и части более длинного dotted-написания
  (`word.A.B.C`, `A.B.Cword`) не распознаются как отдельная цепочка.
  `S.T.A.L.K.E.R.2` даёт `stalker`, `2`. Байтовые границы включают все исходные
  буквы и принятую конечную точку, а нормализованная длина не включает точки.
  Правило лексическое: `a.b.c` тоже превратится в `abc`, даже если это инициалы
  или однобуквенные части доменного имени. Семантического различения нет.
- Комбинируемые знаки U+0300–U+036F сохраняются внутри начатого токена.
  NFC/NFKC не выполняется: `café` и `café` остаются разными термами.
- Прочая пунктуация, пробелы, переводы строк, emoji и NUL разделяют слова.
  Числа, короткие слова и стоп-слова не удаляются.
- Морфологическая обработка не применяется. Один и тот же модуль пригоден
  для документов и запросов. Будущий этап нормализации словоформ подключается
  после токенизатора, сохраняя исходный токен и позицию.

В `tokens.tsv` находятся `document_id`, `field` (`title`/`text`), `position`
(с нуля внутри поля), `begin_byte`, `end_byte` (полуинтервал в исходном поле)
и `term` (нормализованный UTF-8 токен). Например, нормализация `’` уменьшает
байтовую длину терма, но смещения по-прежнему указывают на исходный текст.
Средняя длина считается по Unicode-кодовым точкам нормализованного терма,
включая внутренние соединители и комбинируемые знаки; это не число байтов
и не число видимых графем.

## Формат снимка

В каталоге лежат `corpus.bin`, `documents.jsonl` (соответствие ID и URL)
и `manifest.json` (число документов, источники, размер текста и SHA-256).
ID относятся только к этому снимку; перестраивать индекс следует с его
же таблицей соответствия. HTML не экспортируется.

`corpus.bin` начинается с восьми байтов `MAIIR3\x00\x01`. Далее до EOF:

```text
uint64 document_id
uint32 source_size + source_size ASCII bytes
uint64 title_size  + title_size UTF-8 bytes
uint64 text_size   + text_size UTF-8 bytes
```

Все числа little-endian, длины заданы в байтах. ID положительные и возрастают.
Идентификатор источника соответствует `[a-z][a-z0-9_]{0,63}`.
Длина поля не превышает 64 МиБ. Текст может содержать переводы строк и NUL:
границы определяются длинами, а не специальным разделителем.
Программа удерживает один документ и буфер одного текущего токена;
память не растёт с общим количеством документов. Метаданные URL читаются
отдельно только при необходимости.

## Методика измерений и ограничения

Из одного снимка берутся каждый восьмой, четвёртый, второй документ и весь
снимок. Так в подвыборки попадают разные источники, а тексты не дублируются
для искусственного увеличения объёма. Размер в графике — реальные байты
заголовков и текста без служебных заголовков бинарного формата, КБ = 1000 байт.

На каждой подвыборке выполняется один прогрев и пять измерений, сохраняются
все повторы, минимум, максимум и медиана. `processing_ms` включает сканирование,
нормализацию и счётчики; `elapsed_ms` также включает чтение и разбор формата.
В измеряемых повторах вывод токенов выключен. Время создания процесса
сохраняется отдельно, экспорт MongoDB исключён. Это замеры с прогретым
файловым кешем, а не измерение чтения с холодного диска.

Отдельный полный запуск с `tokens.tsv` показывает стоимость сохранения
результата. В нём `processing_ms` включает форматирование и запись TSV;
его нельзя выдавать за время одного алгоритма. Воспроизводимость привязана
к SHA-256 снимка, версии правил, хешу бинарного файла, компилятору и флагам.

На 21 октября экспорт содержит 12 497 пригодных реальных документов
восьми сайтов (40,3 МБ заголовков и текста). Это всё ещё меньше 30–50 тысяч.
После продолжения обкачки выполните полный запуск с `--config` и новым
`--output`, чтобы создать **новый** снимок и измерить выросший корпус.
Запуск с прежним `--snapshot` намеренно использует прежнее число документов.
Конфигурация `crawler.large.yaml` ограничивает один запуск 30 000 обработанными
URL, а не 30 000 успешно сохранёнными статьями; реальный размер проверяется
по результату экспорта. Экстраполяция и дублирование статей не заменяют замер.

Исходник отчёта: `doc/report_lab3.tex`. После обновления `doc/lab3`:

```powershell
cd doc
pdflatex -interaction=nonstopmode -halt-on-error report_lab3.tex
pdflatex -interaction=nonstopmode -halt-on-error report_lab3.tex
```
