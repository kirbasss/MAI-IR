# ЛР4: словарная лемматизация

Требования находятся в разделе «Лемматизация / Стемминг» файла
`homework_3.md`. Выбран вариант **лемматизации**, не обрезания окончаний.
Работа ведётся в `lab4`; ЛР3 и сохранённые результаты не переписываются.

Краткая памятка всех запусков: [тесты по лабораторным](testing.md).
Только ЛР4: `python run_tests.py --lab 4`; только её C++/GoogleTest и CLI:
`python run_tests.py --lab 4 --cpp-only`. Эти команды работают и в Git Bash,
и в PowerShell, перед тестами C++ автоматически пересобирается.

## Устройство

`cpp/lemmatizer.cpp` — собственный C++-модуль без STL, готовых морфологических
анализаторов и сторонних хеш-таблиц. Массивы выделяются через `malloc/calloc`;
FNV-1a, открытая адресация и линейное пробирование реализованы самостоятельно.
На один вызов `analyze()` память не выделяется. После загрузки анализатор
не меняет словарь; разные потоки могут читать его с отдельными `LemmaResult`,
если никто одновременно не вызывает `load()` и не уничтожает объект.

Данные русского словаря — [OpenCorpora](https://opencorpora.org/?page=downloads).
Основной доступный источник — пакет данных
[`pymorphy3-dicts-ru`](https://pypi.org/project/pymorphy3-dicts-ru/).
В нём записаны словоформы и парадигмы; преобразователь читает эти записи и
восстанавливает нормальную форму из сохранённых префикса, основы и суффикса.
Готовый `MorphAnalyzer`, предсказание неизвестных слов, модель вероятностей
и снятие омонимии **не используются**. Это известные словарные разборы,
а не результаты запуска стороннего лемматизатора на нашем корпусе.

Пакет содержит заранее скомпилированный снимок OpenCorpora, и его нормализация
может отличаться от прямого чтения исходного XML с отдельными лексемами:
при подготовке пакета часть связей уже обработана. Версия, ревизия и хеши
использованных файлов сохраняются; результаты разных источников нельзя
смешивать в одном индексе без пересборки. XML по-прежнему поддерживается:
связь `lemma/l/@t` и `lemma/f/@t` даёт нормальную форму и словоформы, без
дополнительного объединения ссылок. Используются только цельные русские слова,
`ё` сохраняется. Лексикографическая сортировка вариантов нужна для воспроизводимости,
а не для выбора «самого вероятного» разбора.

Данные английского словаря — [Princeton WordNet 3.0](https://wordnet.princeton.edu/).
Самостоятельно реализованы одношаговые замены окончаний по частям речи,
описанные в [документации Morphy](https://wordnet.princeton.edu/documentation/morphy7wn),
и поиск исключений. Результат замены принимается только при наличии основы
в словаре **той же части речи**. Это не вызов библиотеки WordNet и не полная
копия Morphy: обработка словосочетаний, дефисных конструкций и специальных
суффиксов вроде `-ful` не реализована. Служебные слова и новые названия часто
не покрываются WordNet и сохраняются как есть.

Токенизатор `gaming-v3` вызывается до лемматизатора. Он использует STL, как
разрешено для ЛР3. Сам лемматизатор и его CLI не используют контейнеры STL;
CLI получает заимствованный `string_view` только на границе с токенизатором.
GoogleTest и его тестовые фикстуры не являются структурами поисковой системы.
`prepare_lemmas.py` — офлайн-конвертация исходных данных: поток записей,
дедупликация на диске через SQLite, сборка бинарного файла. Для чтения формата
DAWG используется маленький пакет `DAWG2-Python`; это только декодер входных
данных. В обработке документов/запросов Python, DAWG-декодер, XML и SQLite
не участвуют. Собственная хеш-таблица C++ не заменяется сторонней структурой.

Ожидаемая сложность словарного поиска — O(L) для хеширования слова длины L
плюс пробы хеш-таблицы. Для английского выполняется ограниченное число
дополнительных проверок. Это ожидаемая, не гарантированная худшая оценка.
Таблица имеет заполнение не выше 50%; весь корпус в память не загружается.

## Подготовка данных

Официальные словари — данные, не наш исходный код. Их архивы, бинарный
словарь и большие результаты остаются в `data/` и не включаются в Git.

```powershell
python -m pip install -r requirements-lab4.txt
python prepare_lemmas.py --pymorphy --download
```

Команда берёт русский словарь из установленного пакета, а WordNet скачивает
только при отсутствии архива. На сайт OpenCorpora не обращается. Если WordNet
уже скачан, можно вообще обойтись без сети при подготовке:

```powershell
python prepare_lemmas.py --pymorphy --wordnet data/lemma_sources/WordNet-3.0.tar.gz
```

Исходники сайта OpenCorpora и его оригинальный XML для этого пути не нужны.
В манифесте сохраняются версия пакета, исходная ревизия OpenCorpora,
версия декодера и SHA-256 всех использованных файлов данных. Сами пакеты и
словарь в Git не помещаются; версии закреплены в `requirements-lab4.txt`.

Альтернативный прежний вход — исходный XML-архив `.bz2` OpenCorpora. Если он
получен отдельно и оба архива уже лежат локально:

```powershell
python prepare_lemmas.py --opencorpora data/lemma_sources/dict.opcorpora.xml.bz2 --wordnet data/lemma_sources/WordNet-3.0.tar.gz
```

Готовый каталог: `data/lemmas/ru_en_v1/`. В нём находятся `dictionary.bin`,
`manifest.json` с происхождением, SHA-256 входных данных и результата, а также `NOTICE.txt`.
OpenCorpora распространяет материалы под CC BY-SA 3.0; WordNet — под своей
[лицензией](https://wordnet.princeton.edu/license-and-commercial-use).
Конвертация данных не отменяет условий их использования. При передаче
бинарного словаря сохраняйте NOTICE, атрибуцию и применимые условия.

Повторная сборка не перезаписывает опубликованный каталог. Для другой версии
используйте, например, `--output data/lemmas/ru_en_v2`. Версия и хеш словаря
должны быть одинаковыми при обработке документов и поисковых запросов.

Можно собрать только один язык, передав один архив и отдельный `--output`.
Программа явно предупреждает: слова отсутствующего языка останутся неизменными.
Такой прогон нельзя представлять как проверку двуязычной лемматизации.

## Сборка и C++-тесты

Используется уже установленный Docker-образ ЛР3, повторно скачивать его не нужно:

```powershell
docker compose run --rm --no-deps tokenizer-tests
docker compose run --rm --no-deps tokenizer-tests lemmatizer_tests --gtest_color=yes
```

Первый запуск пересобирает CMake-цели и проверяет обе работы. Второй запускает
только уже собранные GoogleTest лемматизатора. Тестовые словари маленькие,
написаны нами и создаются в C++: внешние архивы, MongoDB и сеть не нужны.
Проверяются словоформы, омонимия, `ё`, английские правила и исключения,
неизвестные/специальные токены, UTF-8 и смещения, коллизии, повреждённые файлы,
счётчики CLI, ограничение числа документов и защита выходных файлов.

Офлайн-конвертер проверяется отдельно:

```powershell
python -m unittest -v tests.python.test_lemma_dictionary
```

Оба набора с сохранением журнала в **новый** каталог:

```powershell
python run_lab4.py --output data/lemmatization/checks_001
```

Скрипт сохраняет `tests.txt` и `tests_summary.json`. Если дополнительно
передать `--snapshot`, `--dict` и путь к уже собранному `--binary`, он также
выполнит измерения и сохранит `benchmark.json`. Архивы сам не скачивает.

## Демонстрация и применение

Наглядная таблица «исходное написание → токен → лемма или леммы»
вычисляется **заново C++-анализатором** при каждом запуске:

В **Git Bash** обязательно отключить преобразование Linux-путей:

```bash
MSYS_NO_PATHCONV=1 docker compose run --rm --no-deps tokenizer-tests lemmatizer demo --dict /lemmas/ru_en_v1/dictionary.bin
```

В **PowerShell** выполняется та же Docker-команда без `MSYS_NO_PATHCONV=1`.
Если в Git Bash забыть префикс, словарь может существовать, но программа
получит Windows-путь и ответит `Cannot open dictionary`.

Без Docker, после нативной сборки:

```powershell
build/lemma-native/lemmatizer.exe demo --dict data/lemmas/ru_en_v1/dictionary.bin
build/lemma-native/lemmatizer.exe demo --dict data/lemmas/ru_en_v1/dictionary.bin --input tests/fixtures/lab4_demo.txt
```

Вместо `tests/fixtures/lab4_demo.txt` можно указать свой файл в UTF-8.
В Docker тестовый пример доступен как `/src/tests/fixtures/lab4_demo.txt`.
`--output NEW_FILE.txt` сохраняет таблицу в новый файл, JSON-статистика
поступает в stderr; машинный TSV по-прежнему выдаёт режим `text`.
Колонка «Словарь» сообщает о найденном разборе: «нет» означает сохранение
исходного токена. Позиции начинаются с нуля. Несколько лемм разделены ` | `.

На реальном словаре проверено: `Джозефа → джозеф`, `Джозефу → джозеф`,
`Джо → джо`. Сокращённое имя не является словоформой: переход
`Джозеф → Джо` относится к синонимам, а не к лемматизации.
Он не добавляется в морфологический словарь автоматически.

Проверки алгоритма и демонстрации написаны на **C++ с GoogleTest** в
`tests/cpp/lemmatizer_test_lab4.cpp`. Прогон от 06.11.2026:
`lab4/verification_demo_2026-11-06/tests.txt` — 66 успешных проверок CTest
(общий набор ЛР3–ЛР4, включая 30 GoogleTest лемматизатора, CLI и поиска)
и 17 Python-тестов конвертера и метрик. Python не дублирует правила
лемматизации. Для повторения только C++ GoogleTest ЛР4:

```powershell
docker compose run --rm --no-deps tokenizer-tests lemmatizer_tests --gtest_color=yes
```

Команды для PowerShell. В Git Bash перед Docker-командами с абсолютными
Linux-путями добавьте `MSYS_NO_PATHCONV=1`, чтобы оболочка не меняла пути.

```powershell
docker compose run --rm --no-deps tokenizer-tests lemmatizer text --dict /lemmas/ru_en_v1/dictionary.bin
```

Введите фразу, например `Игроки играли в игры. Games were better. C++ 3.0.1`,
завершите stdin (в Linux-контейнере — Ctrl+D). Конкретные разборы зависят
от версии словаря; это пример ввода, не подставленный заранее результат.
TSV поступает в stdout, JSON со статистикой — в stderr. Для реальных статей
можно обрабатывать тот же бинарный снимок, что и в ЛР3:

```powershell
docker compose run --rm --no-deps tokenizer-tests lemmatizer corpus /corpus/mongodb_2026-10-21/corpus.bin --dict /lemmas/ru_en_v1/dictionary.bin --limit 100
```

Без `--output` режим `corpus` только считает статистику и выводит JSON,
без записи миллионов строк TSV. Столбцы TSV:

```text
document_id  field  position  begin_byte  end_byte  term  lemmas  known
```

`term` — исходный нормализованный токен; `lemmas` — варианты через `|`.
`known=0` означает сохранение исходного токена, а не удаление из поиска.
Это может быть неизвестное слово, защищённый токен или неподключённый язык.
`C++`, `C#`, `PS5`, `3.0.1`, дефисные/апострофные названия не режутся заново.
Позиция и байтовые границы относятся к исходному полю статьи. Несколько лемм
одного слова находятся на **одной позиции**, а не создают новые позиции.

Для «стали» возможны «сталь» и «стать»; для `saw` — `saw` и `see`.
Контекстное снятие омонимии не реализовано. Число альтернатив ограничено 64;
превышение — явная ошибка, не тихое усечение. Просмотр всех вариантов может
повысить полноту и ухудшить точность. Поэтому исходный `term` сохранён для
будущего бонуса точного совпадения, но сам бонус ранжирования ещё не реализован.

`changed_tokens` считает токены, у которых хотя бы один вариант отличается
от исходного; `ambiguous_tokens` — токены с несколькими различными леммами.
Это не метрики правильности морфологического разбора или релевантности.

## Нативный запуск и измерения

Для сборки без Docker нужны только CMake и компилятор (путь сборки новый,
не смешивайте MinGW/MSVC). STL-зависимость остаётся только у токенизатора:

```powershell
cmake -S . -B build/lemma-native -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF -DBUILD_DEMO=OFF
cmake --build build/lemma-native --target lemmatizer --parallel 2
build/lemma-native/lemmatizer.exe text --dict data/lemmas/ru_en_v1/dictionary.bin --input article.txt
build/lemma-native/lemmatizer.exe corpus data/tokenization/mongodb_2026-10-21/corpus.bin --dict data/lemmas/ru_en_v1/dictionary.bin --output data/lemmatization/tokens_001.tsv --stats data/lemmatization/stats_001.json
```

Каталог вывода должен существовать. Существующие файлы и `.part` не
перезаписываются. При обычной ошибке приватный `.part` удаляется; принудительное
завершение процесса может оставить его. Полные файлы публикуются отдельно,
не одной транзакцией на пару TSV/JSON. В stdout до ошибки мог появиться префикс:
всегда проверяйте код возврата. Не направляйте два процесса в один выходной путь.

```powershell
python benchmark_lemmas.py data/tokenization/mongodb_2026-10-21 --dict data/lemmas/ru_en_v1/dictionary.bin --output data/lemmatization/benchmark_001.json
```

Скрипт проверяет SHA-256 снимка и словаря, фиксирует хеш бинарника. Для первых
1/8, 1/4, 1/2 и всех документов: прогрев, пять повторов, медианы. Префиксы могут
различаться по распределению сайтов и языков: это нужно учитывать при сравнении.
`processing_ms` включает токенизацию и лемматизацию, но не чтение файлов и
загрузку словаря; `elapsed_ms` включает чтение корпуса, `load_ms` — отдельный
однократный расход, `process_wall_ms` также включает запуск процесса.
TSV не пишется; память корпуса ограничена текущим полем (до 64 МиБ), словарь
хранится целиком. Замеры прогревают файловый кеш; это не холодное чтение.

относятся к другим снимкам и сохранены как история, не как итоговые значения.
Все словари и корпуса остаются в игнорируемом `data/`.

Сборка нативных утилит (из корня проекта):

```powershell
cmake -S . -B build/lemma-native -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF -DBUILD_DEMO=OFF
cmake --build build/lemma-native --target lemmatizer lemma_search --parallel 2
```

Сам поиск — `cpp/lemma_search.cpp`, C++ без контейнеров STL. Это потоковый
диагностический поиск, а не готовый инвертированный индекс. Три режима
считаются за один обход: `exact`, `lemma`, `hybrid`. Между словами запроса AND,
между леммами одного слова OR. Базовая оценка — покрытие заголовка; гибридный
режим добавляет бонус точных исходных токенов, не меняющий порядок между
разными уровнями покрытия заголовка. При равенстве — ID документа.

### Качество поиска

```powershell
python evaluate_lemmas.py --snapshot data/tokenization/mongodb_2026-10-22_lab4 --dict data/lemmas/ru_en_v1/dictionary.bin --output data/lemmatization/quality_002
python demo_lab4.py
python demo_lab4.py --query q01
```

Каталог `--output` должен быть новым. Пример `quality_002` не меняет уже
выполненный `quality_v1`. Демонстрация читает сохранённый результат из
`doc/lab4/quality.json` и явно об этом сообщает; это Python-представление
результатов настоящего C++ поиска, не отдельный поисковый алгоритм.

В `tests/fixtures/lab4_judgments.json` зафиксированы 12 запросов, 37 реальных
заголовков и предварительные авторские оценки. **Разметку нужно проверить
перед защитой**: это не независимая экспертная оценка. Набор специально
подобран для диагностики, не репрезентативен. Каждая пара размечена, а
отсутствующий в положительном списке ID этого набора явно имеет оценку 0.
Эксперимент использует только заголовки, хотя CLI поддерживает и основной текст.
Recall считается относительно размеченного набора, не всех документов базы.
Средние nDCG@5: 0,282 / 0,824 / 0,862 для exact / lemma / hybrid.
Пример Windows показывает ухудшение при смешении с release windows и
восстановление порядка бонусом; Saw остаётся примером нерешённой неоднозначности.

Для нового живого запуска C++ можно использовать полученные из эксперимента
`corpus.bin` и `queries.tsv` либо свой полный снимок и UTF-8 файл запросов.
Формат строки запросов: `query_id<TAB>текст запроса`. До 64 запросов,
32 различных слов в каждом, top-k от 1 до 100. В stdout — TSV всех трёх режимов:

```powershell
build/lemma-native/lemma_search.exe --corpus data/lemmatization/quality_v1/corpus.bin --dict data/lemmas/ru_en_v1/dictionary.bin --queries data/lemmatization/quality_v1/queries.tsv --top-k 5 --field title
```

### Повторение проверок и отчёта

```powershell
python run_lab4.py --output data/lemmatization/checks_002 --snapshot data/tokenization/mongodb_2026-10-22_lab4 --dict data/lemmas/ru_en_v1/dictionary.bin --quality
```

Docker должен быть запущен, нативные утилиты — предварительно собраны.
После группировки от 07.11.2026 скрипт запускает только ЛР4: 32 проверки CTest
(30 GoogleTest и 2 проверки CLI), 17 Python-тестов
конвертера и метрик, затем замеры и оценку качества. Без `--snapshot` и `--dict`
запускаются только тесты. Проверенный журнал отдельной ЛР4 от 07.11.2026:
`doc/lab4/verification_grouped_2026-11-07/tests.txt`.
`doc/lab4/tests.txt` сохранён как прежний общий прогон 66 проверок ЛР3–ЛР4,
использованный в отчёте; его число нельзя сравнивать с отдельной группой ЛР4.
`--output` должен указывать новый каталог; скрипт не скачивает статьи и не меняет БД.

Для графиков нужен matplotlib (он уже указан в `requirements-lab3.txt`),
для PDF — установленный LaTeX с пакетами из преамбулы, включая `qrcode`.
Исходные результаты замеров под фоновой нагрузкой сохранены в
`doc/lab4/benchmark_full.json`, повторный отдельный замер — в
`doc/lab4/benchmark_final.json`. В отчёте используется второй;
различие показывает чувствительность скорости к состоянию машины.

```powershell
python make_lab4_report.py --benchmark doc/lab4/benchmark_final.json --quality data/lemmatization/quality_v1/quality.json --checks doc/lab4/verification_demo_2026-11-06 --snapshot data/tokenization/mongodb_2026-10-22_lab4 --dictionary data/lemmas/ru_en_v1/dictionary.bin --demo-binary build/lemma-native/lemmatizer.exe
cd doc
pdflatex -interaction=nonstopmode -halt-on-error report_lab4.tex
pdflatex -interaction=nonstopmode -halt-on-error report_lab4.tex
```

Генератор проверяет согласованность SHA-256, обновляет таблицы, график
и компактные данные отчёта в `doc/lab4/`. PDF — `doc/report_lab4.pdf`.
С `--demo-binary` он дополнительно запускает C++ на `tests/fixtures/lab4_demo.txt`,
сохраняет таблицу соответствий и проверяет совпадение счётчиков режимов
`text` и `demo`. `token_examples.tex` включается в отчёт;
`token_examples.tsv`, `token_demo.txt` и `token_demo.json` сохраняют
исходный вывод и контрольные суммы этого отдельного запуска.
QR-код создаётся самим LaTeX и ведёт на исходную ветку `lab4`.
Дополнение отчёта с поиском по большому корпусу находится в ветке `lab8`.

Индекс ЛР7 хранит словоформы и леммы в отдельных пространствах терминов,
с общими ID и метаданными. Индекс содержит списки документов без позиций слов.
Запрос ЛР8 обрабатывается той же парой tokenizer/dictionary.
